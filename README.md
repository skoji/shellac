# shellac

`shellac` is an **incremental-save annotation engine for PDF**, built on
[lopdf](https://crates.io/crates/lopdf). It adds, removes and re-comments
text-markup annotations by appending one incremental update to a document,
so every byte it did not touch stays exactly where it was.

This repository holds three things:

- **`crates/shellac`** — the engine. A Rust library, a C ABI static library
  (the header is generated by cbindgen), and `shellac-cli`, a thin
  command-line wrapper around the same entry point.
- **`crates/verify`** — the `verify` harness, which drives a save engine
  over a corpus of PDFs and reduces the run to a verdict.
- **`corpus/`** — eleven PDF samples covering a range of real-world PDF
  shapes: different producers, encodings, encryption, page structures and
  prior save histories.

The harness exists because incremental save is easy to get subtly wrong in
ways that are hard to notice by eye: a byte that should not have moved did,
a cross-reference chain that should be traversable is not, an annotation
that should still be there silently disappears.

## Why incremental save

A full-rewrite save re-encodes what the writing library understands and
drops what it does not. Apple PDFKit's `PDFDocument.write(to:)` is the
common example: an invisible OCR text layer, which scanned books carry as
Form XObjects, is not something PDFKit preserves, so the text layer is gone
from the file it writes.

The corpus makes that concrete. Sample S5 is sample S1 — a scanned page
with `HiddenVertOCR` / `HiddenHorzOCR` invisible text layers — opened and
saved once through `PDFDocument.write(to:)`. In S5 the OCR text layer does
not survive: `pdftotext` output is effectively empty. See the S5 row of
[`corpus/README.md`](corpus/README.md).

An incremental save cannot lose that way. The original bytes are written
out verbatim and one update is appended after them, linked in by a new
cross-reference section. Whatever the engine did not deliberately change is
still present, byte for byte, because it was never re-encoded.

## The engine's contract

The full contract is in the crate: see
[`crates/shellac/README.md`](crates/shellac/README.md) and the rustdoc on
`shellac::ops`, `shellac::transform` and the crate root.

**Ops.** The engine takes a JSON batch of ops, each one of `add`, `remove`
or `modify_comment`, and applies them in the order given. `annot_id` is the
caller's stable identity for an annotation: it is written to the
annotation's `/NM` entry on `add`, and matched against `/NM` on `remove` and
`modify_comment`. When `/NM` does not match, `remove` and `modify_comment`
fall back to `subtype` plus `/Rect contains(user_point)`. An `add` whose
`annot_id` is already on that page — in the document, or queued earlier in
the same batch — is rejected as `add_duplicate_nm`; the check is per page,
so the same `annot_id` on two different pages is not a duplicate and a
caller wanting document-wide unique ids has to enforce that itself.

**Coordinates.** `rect`, `quad_points` and `user_point` are all in raw PDF
user space — MediaBox-absolute, y-up, unrotated, the same space the file
itself stores in `/Rect`. No coordinate-space conversion happens on the way
in, which is what makes `/Rotate` a non-event for a caller that already
holds user-space coordinates — PDFKit's `PDFSelection.bounds(for:)` and
`PDFAnnotation.bounds` do, on every rotation.

A caller that does not is on the hook for the conversion. Rectangles
computed in a `/Rotate`-applied display frame — from view-space touches on
a rotated page, or hand-built by a debug tool — have to go through
`shellac::transform::rect_page_space_to_user` first; `apply_ops` will not
do it for them. `shellac::transform` documents both the transforms and
which PDFKit APIs have and have not been verified against user space.

The three fields are used differently. `rect` goes into `/Rect` as given.
`user_point` is never written to the file at all: it is how a `remove` or
`modify_comment` finds its target when `/NM` does not match, by testing
which annotation's `/Rect` contains it. `quad_points` goes into
`/QuadPoints` as given, with one exception. A `Highlight` quad taller than
it is wide, which is what a run of vertical Japanese text produces, is
written as the four corners of that quad's axis-aligned bounding box, in
Acrobat's `[BL, TL, BR, TR]` order, because Acrobat's built-in QuadPoints
rasterizer draws a bow-tie for such a quad in any other order. For the
axis-aligned quads callers normally send, that is a reordering of the same
four points; for a tilted quad it substitutes the box that encloses them,
so the emitted coordinates need not appear in the input at all. Wide
quads, and `Underline` / `StrikeOut` / `Squiggly` at any aspect ratio, are
written as given.

**Statuses.** `ApplyResult.status` is one of `ok`, `parse_failed`,
`io_failed`, `encrypted_refused` or `annotations_restricted`. Ops that could
not be applied are reported individually in `skipped` with a reason
(`add_page_not_found`, `add_duplicate_nm`, `remove_page_not_found`,
`remove_target_not_found`, `modify_page_not_found`,
`modify_target_not_found`); a skipped op is not a failure, so the overall
status stays `ok`. If nothing was applied, the file is not written at all.

**Probing.** `shellac_can_open(path)` classifies a document before any batch
is queued:

| Code | Meaning |
|---:|---|
| 0 | ok — parsed, not encrypted |
| 1 | parse_failed |
| 2 | io_failed |
| 3 | invalid_arg (NULL pointer or non-UTF-8 path) |
| 4 | panic (caught at the FFI boundary) |
| 5 | password_required — encrypted, and the empty user password did not open it |
| 6 | encrypted — encrypted, and the empty user password did open it |
| 7 | annotations_restricted — as 6, but `/P` clears the `ANNOTABLE` bit |

**Encryption policy.** A document that the empty user password opens is
decrypted in place by lopdf, which retains the encryption state; the
incremental update is then re-encrypted under that same key, so the
round-trip is safe. A document that needs a real password is refused
(`encrypted_refused`) — there is no key to encrypt an increment under. A
document whose `/P` clears the `ANNOTABLE` bit is refused as well
(`annotations_restricted`), because its producer disallows annotation
edits. Both refusals leave the file byte-for-byte untouched.

**Panic safety.** Every FFI entry point is wrapped in
`std::panic::catch_unwind`, so a panic never unwinds across the C ABI
boundary. `panic = "abort"` disables `catch_unwind` and therefore MUST NOT
be set on any profile — see the comment in the workspace `Cargo.toml`.

## Using it

**As a Rust library.** `shellac::ops::apply_ops(path, batch)` is the entry
point; it returns an `ApplyResult`. `shellac::ops` also carries the wire
types (`OpsBatch`, `AnnotationOp`, `UserRect`, `UserPoint`, `ApplyResult`,
`Status`, `SkipReason`), `shellac::transform` the coordinate contract and
its rotated-page-space conversions, and `shellac::annots` the annotation
dictionary and incremental-save helpers the engine is built from.

```toml
[dependencies]
shellac = "0.1"
```

**As a C static library.** The crate builds as a `staticlib` and exposes
three symbols — `shellac_apply_ops`, `shellac_can_open`,
`shellac_free_string` — declared in
[`crates/shellac/include/shellac.h`](crates/shellac/include/shellac.h).
`build.rs` regenerates it from the current FFI surface into `OUT_DIR` on
every build (verified fresh by a test), and a maintainer refreshes the
committed copy with `SHELLAC_UPDATE_HEADER=1 cargo build -p shellac` after
changing that surface. For Apple platforms,
`scripts/build-xcframework.sh` builds the device and simulator slices and
packages them, with the header and a module map, as `Shellac.xcframework`:

```sh
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
bash scripts/build-xcframework.sh
```

**As a command-line tool.** `shellac-cli` owns no PDF-writing logic of its
own — every save routes through `apply_ops`, which is what lets a corpus run
double as a smoke test of the engine itself. Its subcommands are the
harness's scenarios:

```sh
shellac-cli add <pdf> [--hl-rect llx,lly,urx,ury] [--ul-rect llx,lly,urx,ury]
shellac-cli remove <pdf>
shellac-cli loop-one <i> <pdf> [--rect llx,lly,urx,ury]
shellac-cli modify-comment <new-contents> <pdf>
shellac-cli add-multiline <pdf> --hl-quads "x0,y0,x1,y1,x2,y2,x3,y3;..."
shellac-cli check-ap <pdf>
```

`add` writes a highlight and an underline to page 1 as one increment;
`remove` takes both away again; `loop-one` adds one highlight per iteration
for repeated-save runs; `modify-comment` changes the highlight's
`/Contents`; `add-multiline` adds one highlight whose `/QuadPoints` spans
several rectangles; `check-ap` asserts the appearance stream the engine
generates for a highlight.

## How it is verified

The corpus is eleven samples — see [`corpus/README.md`](corpus/README.md)
for what each one exists to exercise, how the generated ones are rebuilt,
and where the source text comes from. Five are committed under
`corpus/fixtures/`; the rest are produced on demand by the scripts in
`corpus/generators/`.

For each sample the harness runs a fixed sequence of scenarios — add,
modify-comment, add-multiline, remove, and ten repeated incremental saves —
and evaluates each one against this catalogue:

| Check | What it asserts |
|---|---|
| C1 | forward byte immutability: the previous revision is a byte-identical prefix of the new file |
| C2 | `%%EOF` marker count grows by exactly 1 per incremental save |
| C3 | increment audit: appended bytes end in `startxref` and contain no font re-embedding tokens |
| C4 | pdftotext extraction unchanged (whitespace-normalized comparison) |
| C5 | PDFKit text extraction unchanged (exact comparison) |
| C6 | annotation presence/absence via qpdf JSON: the `/NM` object exists and is attached to a page's `/Annots` |
| C6-quads | `/QuadPoints` shape survives the round-trip (add-multiline only: >= 16 floats, multiple of 8) |
| C7 | PDFKit reload: document loads, page count and expected `/NM` set match, thumbnails render |
| C8 | repeated-save endurance: 10 loop iterations all pass and each increment stays under 50KB |
| C11a | position verification, independent path: pdftotext `-bbox-layout` needle bounds vs the `/Rect` read back via qpdf (tolerance 3pt) |
| C11b | position verification, PDFKit path: re-located needle bounds vs annotation bounds (tolerance 3pt) |
| C-enc-qpdf | encrypted round-trip integrity: `qpdf --check --password=` after each scenario (encrypted roundtrip fixtures only) |
| Encrypted | encrypted-path aggregate: C-enc-qpdf results for roundtrip fixtures, or the refusal contract (expected status + file unchanged) for refused fixtures |

C9 and C10 record rather than judge: the document `/Producer` as seen by
pdfinfo and exiftool, and the `/AP` shape of the written annotation. They
appear in the report as recorded items with no verdict attached.

### Continuous integration

The full matrix runs on every push, over the whole corpus, driving
`shellac-cli` as the save engine. It runs twice, because no single machine
can evaluate every check: Linux covers everything reachable with qpdf and
poppler, and macOS adds C5, C7 and C11b, which are made of PDFKit. The
generated samples are built once on Linux and handed to the macOS job.

Each check is a script under `scripts/ci/`, so any CI failure can be
reproduced locally by running the same command:

```sh
bash scripts/ci/check-generated-samples.sh     # regenerate S3, S8..S12 and assert their structure
bash scripts/ci/audit-fixtures.sh              # committed fixtures carry no identifying content
bash scripts/ci/check-fixture-invariants.sh    # S4 prefix/revision/annotation and S5 xref invariants
bash scripts/ci/assemble-samples.sh <gen> <samples>  # generated samples + committed fixtures in one directory
bash scripts/ci/build-swift-helpers.sh         # compile the PDFKit helpers (macOS)
bash scripts/ci/run-matrix-linux.sh <samples>  # the matrix without the PDFKit helpers
bash scripts/ci/run-matrix-macos.sh <samples>  # the matrix with every check (macOS)
```

`check-generated-samples.sh` takes an optional directory to build the
samples in; passing one keeps them between runs, which is worth doing
locally because S3 is rendered and OCR'd from scratch.

The two matrix scripts take a directory holding the corpus to run over —
the generated samples plus the committed fixtures, which is what
`assemble-samples.sh` produces — and an optional directory for the report.
Nothing in `run-matrix-linux.sh` is actually Linux-specific: running it on
macOS is how the PDFKit-free mode is checked.

### Known exceptions

`corpus/known-exceptions.json` records check outcomes that are understood
and accepted rather than treated as defects — for example a position check
whose two measurement paths disagree about vertical Japanese text. Each
entry names the samples, checks, and scenarios it covers and states why, so
that tolerating an outcome is a reviewable decision in the repository rather
than a special case buried in the harness. Entries are matched one failing
cell at a time, and failures that must not be excused by association carry
check ids of their own — a save operation that failed, an incremental save
that grew past the endurance limit — so that an entry written about one
finding cannot absorb another.

The list is what makes CI usable: `verify gate` matches a run's failing
cells against it, and only an unmatched failure fails the build. A failed
save operation is never matched — no entry can excuse an engine that could
not write the file. Every CI run also feeds the gate a committed failure
that no entry covers and requires the rejection, so a gate that had started
accepting everything cannot pass for a clean run.

## Status

Published as-is under MIT. There is no support commitment and no
response-time promise: issues and pull requests are welcome, but they may go
unanswered.

The Rust API may change before 1.0. The JSON ops contract is intended to
stay backward compatible — the `annot_id` field, for instance, is also
accepted under the alternative key `shelff_id`, and aliases like that are
kept rather than dropped.

## Relationship to shelff

`shellac` is the save engine of [shelff](https://skoji.dev/en/shelff/), an
iPadOS PDF reader by the same author. The crate contains no shelff-specific
code: it is a general-purpose PDF annotation engine, and everything it does
is described by the contract above.

## Toolchain and requirements

The Rust toolchain is pinned by [`rust-toolchain.toml`](rust-toolchain.toml)
to 1.95.0, so a local build and a CI build agree without either side naming
a version. Building the engine needs nothing beyond that.

The harness needs external tools:

- **qpdf** and **poppler** (`pdftotext`, `pdfinfo`) — required.
- **exiftool** — optional; without it the C9 exiftool column is left empty.
- **macOS** — required for C5, C7 and C11b, which are built from PDFKit via
  the Swift helpers in `scripts/`.

Rebuilding the generated corpus samples additionally needs `img2pdf`,
`ocrmypdf`, `tesseract` (with the `jpn` language pack) and a Python
interpreter with Pillow; see [`corpus/README.md`](corpus/README.md).
